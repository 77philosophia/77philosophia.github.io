pytorch里的jit加速

Posted on 2026-07-27 In 专业笔记

pytorch with jit

  • 不使用jit:
    • cpu和gpu频繁切换。比如：在具身智能的交互循环中，CPU 需要频繁地把观测数据（Observations）发给 GPU，等 GPU 算完后再把动作（Actions）和奖励（Rewards）传回 CPU。
    • 使用jitting:通过 @torch.jit.script 或 torch.jit.trace，PyTorch 可以把整个模型或核心前向传播过程“编译”成一个独立于 Python 的静态图。这样 GPU 就可以脱离 Python 解释器的逐行控制，大幅减少内核启动开销（Kernel launch overhead），从而提升推理和训练速度。

是不是都可以用jit

  • 动态控制流的限制:对频繁的if/else等动态控制流支持不好
  • 调试困难
  • cpu和io密集型任务不适合

最佳实践

  • 局部优化：只对 Agent 中计算最密集、调用最频繁的神经网络核心模块（例如 policy 推理函数或网络前向传播）使用 @torch.jit.script 或 torch.jit.trace。
  • 先调通，再加速：关闭jit写代码，打开jit大规模并行

经典使用jit的例子

在具身智能和强化学习（例如 Dreamer 算法或在线控制策略）中，最经典、最适合使用 JIT 的模块是 智能体的策略网络前向推理（Policy Forward Pass / Action Sampling Module）

加速原因

  • 摆脱 Python 解释器的逐行调度开销
    • 普通 PyTorch：Python 每执行一行神经网络计算，都要经过 Python 解释器，然后通过 C++ 接口去调用底层 CUDA 算子。如果每一步交互的计算量很小（比如强化学习中单步推理），Python 调度本身消耗的时间甚至会超过 GPU 实际计算的时间。
    • JIT 优化后：整个模型被编译成了一个纯 C++ 层的执行图（Graph），在运行大循环时完全绕过了 Python 解释器，让 GPU 可以连续不断地全速运算。
  • 算子融合（Operator Fusion）
    • 普通 PyTorch：对于 Linear -> ReLU -> Linear 这种常见组合，GPU 通常需要执行三次独立的 Kernel（内核启动）：先算完线性层写回显存，再启动一个 Kernel 做 ReLU，再启动一个 Kernel 做第二个线性层。中间伴随着频繁的显存读写（Memory Bottleneck）。
    • JIT 优化后：编译器会自动将这些相邻的小算子“融合”成一个单一的复合算子（Fused Kernel）。数据直接在 GPU 寄存器/缓存中流转，大幅减少了显存带宽的消耗。
  • 常量折叠与死代码消除（Constant Folding & Dead Code Elimination）
    • JIT 在编译时会预先计算好那些在运行期不会改变的静态表达式（常量折叠），并剔除掉永远不会被执行的分支代码，从而精简最终的计算图。
  • 更好的底层硬件优化：TorchScript 能够以更全局的视角审视整个计算图，产生更优的机器码

理解原生 PyTorch（Eager Mode，即动态图模式）在执行神经网络计算时，Python 代码和底层硬件（GPU/CPU）之间是如何交互的。
